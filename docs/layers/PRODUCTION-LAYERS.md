# Production layers checklist

Filled in during Phase 1 (2026-11-14). For each layer: applies? → decision → how it's enforced (rule / test / hook / CI) → phase. "Now" is this technical test. "Production" is what would change for a real deployment. Layers that don't apply are marked `N/A + reason`; none are skipped.

| Layer | Applies? | Decision | Enforced by | Phase |
|---|---|---|---|---|
| Frontend | **N/A**: the spec asks for a JSON API only, with no UI. OpenAPI + Scalar is the only browser surface, for developers. | No frontend. If one were added: minified builds, private source maps, no secrets in the bundle. | `AGENTS.md` purpose ("Backend only, no UI") | — |
| Database | Yes | **Now:** EF Core + SQLite. Money as `decimal` with `HasPrecision(18,2)`, enums stored as strings, application → assessments one-to-many, indexes on `OwnerId` and `ApplicationId`, versioned migrations. **Production:** Azure SQL (same EF model, a provider swap), automated backups, point-in-time restore. | Migrations merged to `main` can't be edited (`protect-files.sh`); integration tests run against a real SQLite DB | 3 (model + migration), 4 (volume), 9 (WAL, indexes measured) |
| Auth & permissions | Yes | **Owner scoping from Phase 3.** Every query is `Id = @id AND OwnerId = @owner`. `OwnerId` comes only from the current-user abstraction (`ICurrentUser`), never from the request body. **Phase 7 (built):** JWT bearer with issuer, audience, lifetime and signature validated; ES256 only (ECDSA P-256, `ValidAlgorithms` pinned), `RequireSignedTokens`, `RequireExpirationTime`, `ClockSkew` 30 s, `MapInboundClaims = false`, no error details in `WWW-Authenticate`. The validation key is `Jwt:SigningPublicKey` (PEM); startup fails outside `Development` if it's missing. Secure by default: fallback policy `RequireAuthenticatedUser`, with `AllowAnonymous` only on `/health`, the dev token endpoint and, in `Development` only, the OpenAPI document and Scalar. `OwnerId` comes from `sub` (`ClaimsCurrentUser`); a missing, blank or over-long `sub` is a 401. Another user's data returns 404. **Dev token endpoint fails closed** (S2): `POST /dev/token` is registered only in `Development` **and** with `DevAuth:Enabled=true`, signs with a key pair generated in memory at startup (then the only trusted key), and startup throws if the flag is on in any other environment or together with a configured `Jwt:SigningPublicKey`. Trust comes only from `Jwt:*` (the handler's `Authority` and `MetadataAddress` are cleared). Rejected tokens write an app-owned `TokenRejected` event with the failure type only. **Production:** Entra ID / OIDC, single-tenant issuer + audience, owner keyed on `oid`+`tid`; the dev endpoint isn't registered. Least privilege: users see only their own applications. | `.claude/rules/security.md`; integration tests for 401 without or with a bad/expired token, cross-user 404, and dev token endpoint 404 under `Production` | 3 (owner scoping), 7 |
| Version control | Yes | One branch and PR per phase, squash-merged. Conventional commits. No force push, no `--no-verify`. Gitleaks on every commit. **Open:** branch protection on `main` requiring the CI check (Alessandro to enable). | `block-dangerous-bash.sh`, `.githooks/pre-commit` (Gitleaks), CI on every PR | 0 (done); protection: Alessandro |
| APIs | Yes | Minimal APIs (`MapGroup`, `TypedResults`), public DTO records (never entities), `AddValidation` → 400 `ValidationProblemDetails`, `AddProblemDetails` + `IExceptionHandler` with a trace ID (no exception details outside Development), OpenAPI 3.1 + Scalar mapped in **Development only**, no CORS policy (no browser client; the default denies cross-origin requests), `201` + `Location` on create. Declined is a 200 result, not an error. Idempotency: assessment creation is not idempotent by key in this test (each POST is a new assessment); documented as a production next step (`Idempotency-Key` header). | `.claude/rules/backend.md`; integration tests (400 on invalid input, 201 + Location, 404) | 3, 6 (202 + Location for background) |
| Hosting / deploy | Yes | **Now:** multi-stage Dockerfile (sdk:10.0 → aspnet:10.0), non-root `USER $APP_UID`, port 8080, compose with a SQLite volume, `/health`, config via environment variables. Migrations run on startup in dev only (ADR in Phase 4). **Production:** build the image once and promote it through environments, run migrations as a separate step, roll back by redeploying the previous image tag, readiness check including the DB. | `docker build` in CI; fresh-clone rehearsal | 4, 5 (DB health check), 11 |
| Security | Yes | OWASP Top 10:2025 mapping with evidence, Semgrep, Gitleaks (history), `dotnet list package --vulnerable`, input limits (rules section 1), no PII or money in logs. **Phase 8 (built):** `SecurityHeadersMiddleware` (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` on all responses), `UseHsts()` outside `Development`, `AllowedHosts` set to `"localhost;127.0.0.1"` (P8-D3 A). Supply chain: SHA-pinned actions; `nuget.config` with `<packageSourceMapping>` (`nuget.org` over HTTPS only), `<RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>`, 5 committed `packages.lock.json` files, `dotnet restore --locked-mode` in `verify.sh`, `Dockerfile` and CI (P8-D4 A); multi-arch `@sha256:...` digests in `Dockerfile` and `compose.observability.yaml`, plus `.github/dependabot.yml` for `nuget`, `docker` and `github-actions` (P8-D5 A); `block-dangerous-bash.sh` blocks shell writes to `.claude/hooks/**` and `.claude/settings*.json` (P8-D6 A). | `security-auditor` gate every phase; `/security-review` on every PR; `SecurityHardeningTests`, `ComposeFileTests`, `test-hooks.sh` | every phase; 8 (done) |
| Rate limiting | Yes | **Phase 8 (built, P8-D1 A):** `AddRateLimiter` (`RateLimitingSetup`) with a shared `"write"` fixed-window policy on `POST /api/applications`, `POST /api/applications/{id}/assessments`, and `POST /dev/token`, partitioned per authenticated `sub` (`"sub:{sub}"`, and `"dev-token"` on `/dev/token`), `QueueLimit = 0`, returning 429 `ProblemDetails` + `Retry-After`. `RateLimiting:PermitLimit` (`1..10,000`, default 60) and `RateLimiting:WindowSeconds` (`1..3,600`, default 60) validated at startup. Authentication runs before rate limiting so anonymous callers get 401 and cannot consume permits. **Production:** also at the gateway (Azure API Management / Front Door). | `RateLimitingTests`, `StartupTests` | 8 (done) |
| Caching | **N/A for now**: the data is per-user and written as often as it's read; there's no measured hot path. B5 says caching only where measured. | No cache. Revisit only if Phase 9 measurements show a hot read path. Then use output caching on `GET` with a per-user vary key, never shared across users. | Phase 9 measurements decide | 9 (measure only) |
| Scaling | Yes | **Now:** a stateless API tier; assessments run in a background worker fed by an in-process bounded `Channel` behind `IAssessmentQueue`, with Pending items re-enqueued on startup. A full queue never drops work silently (S6): `FullMode = Wait` bounded by `Assessments:EnqueueTimeoutSeconds` (default 10 s, `1..300`, P8-D2 A), returning 503 `ProblemDetails` while keeping the `Pending` row in SQLite for startup recovery. **First bottleneck at load:** SQLite's single writer and the in-process queue, both tied to one instance. **First change:** move to Azure SQL and swap `IAssessmentQueue` for a durable queue (Azure Service Bus), so several API and worker instances can scale out independently. | ADR 0003 in Phase 6; `AssessmentWorkerTests` (S8-22) in Phase 8; a k6 baseline in Phase 9 | 6, 8, 9, 10 (README scaling answer) |
| Observability | Yes | Structured `ILogger` with `[LoggerMessage]`; OpenTelemetry tracing (ASP.NET Core + HTTP + a custom span per assessment) and metrics (assessments by decision, duration histogram), OTLP export to the Aspire dashboard in dev. The trace ID is in every ProblemDetails. **Allowlist** (rules §6, `security-auditor` S3): logs, span attributes and metric tags carry only the application ID, assessment ID, decision, `RulesVersion`, status codes and timings. Never inputs, and never output values (loan, LTV, DTI, LTI, payment, max borrowing, summary, checks) or tokens. No HTTP body logging, no EF `EnableSensitiveDataLogging`, and validation and exception messages never echo submitted values. | `AGENTS.md` + `.claude/rules/backend.md`; a test asserting that none of an assessment's input or output numbers (raw or formatted) appear in captured logs or spans | 5 |
| Data / compliance | Yes (by design, light) | Financial data is personal data under UK/EU GDPR. Now: data minimisation (only the five fields plus the owner ID; no name or address), owner-scoped access, no PII in logs, assessments keep their `RulesVersion` and timestamps (an audit trail of what rule produced which decision). **Production:** a retention policy and deletion endpoint, encryption at rest (Azure SQL TDE), a full audit log. Not built in this test. | `.claude/rules/security.md`; the log test (Phase 5) | 3, 5; retention: README next steps |
| Cost | Yes (low) | Now: zero cloud cost; SQLite and the in-process queue need no paid services. **Production:** Azure Container Apps (scale to zero for low traffic) + Azure SQL serverless + Service Bus Basic/Standard; cost grows mainly with DB and queue tiers. Mentioned in the README, not built. | — (README) | 10 |
| AI features | **N/A in the product**: the API has no AI features; the affordability logic is deterministic. AI is used only to build and review the code. | For the engineering process: prompts are logged verbatim (`docs/ai/PROMPTS.md`), every PR gets fresh-context reviews, a human approves every merge, and guardrails are enforced by hooks and permission rules. | `.claude/` hooks + settings; `PROMPTS.md`; Checkpoint A/B approvals | every phase |
