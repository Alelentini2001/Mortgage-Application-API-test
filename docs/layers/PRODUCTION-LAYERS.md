# Production layers checklist

Filled in during Phase 1 (2026-11-14). For each layer: applies? → decision → how it's enforced (rule / test / hook / CI) → phase. "Now" is this technical test. "Production" is what would change for a real deployment. Layers that don't apply are marked `N/A + reason`; none are skipped.

| Layer | Applies? | Decision | Enforced by | Phase |
|---|---|---|---|---|
| Frontend | **N/A**: the spec asks for a JSON API only, with no UI. OpenAPI + Scalar is the only browser surface, for developers. | No frontend. If one were added: minified builds, private source maps, no secrets in the bundle. | `AGENTS.md` purpose ("Backend only, no UI") | — |
| Database | Yes | **Now:** EF Core + SQLite. Money as `decimal` with `HasPrecision(18,2)`, enums stored as strings, application → assessments one-to-many, indexes on `OwnerId` and `ApplicationId`, versioned migrations. **Production:** Azure SQL (same EF model, a provider swap), automated backups, point-in-time restore. | Migrations merged to `main` can't be edited (`protect-files.sh`); integration tests run against a real SQLite DB | 3 (model + migration), 4 (volume), 9 (WAL, indexes measured) |
| Auth & permissions | Yes | **Now:** JWT bearer (issuer, audience, lifetime, key ≥ 256 bits from config) and a dev-only token endpoint (Development/Docker only). Every endpoint except `/health` and the dev token endpoint requires authorization. Resources are scoped to the caller's `OwnerId`; another user's data returns 404. **Production:** Entra ID / OIDC as the identity provider; the dev token endpoint is not registered. Least privilege: users see only their own applications. | `.claude/rules/security.md`; integration tests for 401 without or with a bad token and cross-user 404 | 7 |
| Version control | Yes | One branch and PR per phase, squash-merged. Conventional commits. No force push, no `--no-verify`. Gitleaks on every commit. **Open:** branch protection on `main` requiring the CI check (Alessandro to enable). | `block-dangerous-bash.sh`, `.githooks/pre-commit` (Gitleaks), CI on every PR | 0 (done); protection: Alessandro |
| APIs | Yes | Minimal APIs (`MapGroup`, `TypedResults`), public DTO records (never entities), `AddValidation` → 400 `ValidationProblemDetails`, `AddProblemDetails` + `IExceptionHandler` with a trace ID, OpenAPI 3.1 + Scalar, `201` + `Location` on create. Declined is a 200 result, not an error. Idempotency: assessment creation is not idempotent by key in this test (each POST is a new assessment); documented as a production next step (`Idempotency-Key` header). | `.claude/rules/backend.md`; integration tests (400 on invalid input, 201 + Location, 404) | 3, 6 (202 + Location for background) |
| Hosting / deploy | Yes | **Now:** multi-stage Dockerfile (sdk:10.0 → aspnet:10.0), non-root `USER $APP_UID`, port 8080, compose with a SQLite volume, `/health`, config via environment variables. Migrations run on startup in dev only (ADR in Phase 4). **Production:** build the image once and promote it through environments, run migrations as a separate step, roll back by redeploying the previous image tag, readiness check including the DB. | `docker build` in CI; fresh-clone rehearsal | 4, 5 (DB health check), 11 |
| Security | Yes | OWASP Top 10:2025 mapping with evidence, Semgrep, Gitleaks (history), `dotnet list package --vulnerable`, input limits (rules section 1), no PII or money in logs, security headers/HSTS outside Development, `AllowedHosts` set. Supply chain: SHA-pinned actions now; NuGet lock files, source mapping and Dependabot in Phase 8 (D12). | `security-auditor` gate every phase; `/security-review` on every PR; a log test in Phase 5 | every phase; 8 (hardening) |
| Rate limiting | Yes (optional) | `AddRateLimiter` with a fixed-window policy on the POST endpoints, per user, 429 on excess. Needs Alessandro's approval in Phase 8 (B5 marks it optional). **Production:** also at the gateway (Azure API Management / Front Door). | an integration test for 429 if adopted | 8 (optional) |
| Caching | **N/A for now**: the data is per-user and written as often as it's read; there's no measured hot path. B5 says caching only where measured. | No cache. Revisit only if Phase 9 measurements show a hot read path. Then use output caching on `GET` with a per-user vary key, never shared across users. | Phase 9 measurements decide | 9 (measure only) |
| Scaling | Yes | **Now:** a stateless API tier; assessments run in a background worker fed by an in-process bounded `Channel` behind `IAssessmentQueue`, with Pending items re-enqueued on startup. **First bottleneck at load:** SQLite's single writer and the in-process queue, both tied to one instance. **First change:** move to Azure SQL and swap `IAssessmentQueue` for a durable queue (Azure Service Bus), so several API and worker instances can scale out independently. | ADR in Phase 6; a k6 baseline in Phase 9 | 6, 9, 10 (README scaling answer) |
| Observability | Yes | Structured `ILogger` with `[LoggerMessage]`; OpenTelemetry tracing (ASP.NET Core + HTTP + a custom span per assessment) and metrics (assessments by decision, duration histogram), OTLP export to the Aspire dashboard in dev. The trace ID is in every ProblemDetails. **No income, expenses, deposit, property value or tokens in logs or spans.** | `AGENTS.md` + `.claude/rules/backend.md`; a test asserting that no monetary values appear in logs | 5 |
| Data / compliance | Yes (by design, light) | Financial data is personal data under UK/EU GDPR. Now: data minimisation (only the five fields plus the owner ID; no name or address), owner-scoped access, no PII in logs, assessments keep their `RulesVersion` and timestamps (an audit trail of what rule produced which decision). **Production:** a retention policy and deletion endpoint, encryption at rest (Azure SQL TDE), a full audit log. Not built in this test. | `.claude/rules/security.md`; the log test (Phase 5) | 3, 5; retention: README next steps |
| Cost | Yes (low) | Now: zero cloud cost; SQLite and the in-process queue need no paid services. **Production:** Azure Container Apps (scale to zero for low traffic) + Azure SQL serverless + Service Bus Basic/Standard; cost grows mainly with DB and queue tiers. Mentioned in the README, not built. | — (README) | 10 |
| AI features | **N/A in the product**: the API has no AI features; the affordability logic is deterministic. AI is used only to build and review the code. | For the engineering process: prompts are logged verbatim (`docs/ai/PROMPTS.md`), every PR gets fresh-context reviews, a human approves every merge, and guardrails are enforced by hooks and permission rules. | `.claude/` hooks + settings; `PROMPTS.md`; Checkpoint A/B approvals | every phase |
