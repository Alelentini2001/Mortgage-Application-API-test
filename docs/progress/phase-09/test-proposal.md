# Phase 9 Test Design — Optimisation + Quality (`P9-D1` to `P9-D4`)

Proposed test cases for [phase-09-quality.md](file:///Users/ale_ssd/Developer/Mortgage-Application-API-test/docs/progress/phase-09-quality.md), grouped by category. Nothing is assumed approved until Alessandro selects the cases.

### Happy path

1. **`P9-T1` (`must`) — Stored `RulesVersion` returned by `ProcessAssessmentAsync` on `Completed` and forwarded to telemetry**
   `P9-T1 | given an application with E1 inputs (AnnualIncome=85,000.00, MonthlyExpenses=900.00, DepositAmount=60,000.00, PropertyValue=300,000.00, TermYears=30), a Pending assessment, and AffordabilityCalculator configured with RulesVersion="1.0" (plus a custom-version unit test with RulesVersion="2.1") | when MortgageApplicationService.ProcessAssessmentAsync(assessmentId) completes (unit test in MortgageApplicationServiceTests) and AssessmentWorker processes an item (AssessmentSpanTests / AssessmentMetricTests) | then AssessmentProcessingResult equals (Outcome: Completed, ApplicationId: application.Id, Decision: Approved/Declined, RulesVersion: "1.0" or "2.1"), and the assessment.process span and both metric instruments carry a single assessment.outcome="Completed" tag and assessment.rules_version equal to the stored result.RulesVersion | why it matters: proves telemetry tags Completed assessments with the rules version actually stored on AffordabilityResult rather than re-reading live options, and avoids duplicate OutcomeTag writes (PR #9 /code-review 2–3).`

2. **`P9-T2` (`must`) — `FindForProcessingAsync` projects scalar inputs without tracking `MortgageApplication`, and `UpdateAssessmentAsync` modifies only changed columns on tracked assessments**
   `P9-T2 | given a seeded MortgageApplication (E1: 85,000.00, 900.00, 60,000.00, 300,000.00, 30) and a Pending AffordabilityAssessment in SQLite | when EfMortgageApplicationRepository.FindForProcessingAsync(assessment.Id) is called on a scoped MortgageApplicationsDbContext, followed by work.Assessment.Complete(result, assessedAt) and UpdateAssessmentAsync(work.Assessment) | then (1) after FindForProcessingAsync, work.Inputs == E1, db.ChangeTracker.Entries<MortgageApplication>() is empty (count = 0), and db.ChangeTracker.Entries<AffordabilityAssessment>() has 1 entry in EntityState.Unchanged; (2) after Complete(...), the tracked entry has IsModified == true only on Status, Result, and AssessedAt, and IsModified == false on Id, ApplicationId, CreatedAt, and FailedAt (and UpdateAssessmentAsync does not call DbSet.Update on the already-tracked entity, so those immutable properties stay IsModified == false); (3) a fresh DbContext reloads Status == Completed, Result == expected, AssessedAt == assessedAt | why it matters: avoids materializing/tracking the parent MortgageApplication and ensures EF Core's UPDATE statement writes only changed columns (PR #8 /code-review 3).`

3. **`P9-T3` (`must`) — SQLite `EXPLAIN QUERY PLAN` confirms index / primary-key `SEARCH` (no full-table `SCAN`) on repository lookups**
   `P9-T3 | given a migrated SQLite database with seeded MortgageApplication and AffordabilityAssessment rows | when EXPLAIN QUERY PLAN is executed on the SQL commands generated by EfMortgageApplicationRepository.FindAsync(id, ownerId), FindAssessmentAsync(applicationId, assessmentId, ownerId), FindForProcessingAsync(assessmentId), and owner/application foreign-key lookups (MortgageApplications by OwnerId, AffordabilityAssessments by ApplicationId) | then every returned query-plan detail line contains "SEARCH" with a primary key or index ("USING INDEX IX_MortgageApplications_OwnerId", "USING INDEX IX_AffordabilityAssessments_ApplicationId", or primary-key search on sqlite_autoindex / INTEGER/TEXT PK) and 0 plan lines contain "SCAN" | why it matters: proves by automated test that point and foreign-key queries use indexes rather than table scans (P9-D2, PRODUCTION-LAYERS.md "Database").`

4. **`P9-T4` (`must`) — `MigrateDatabaseAsync` enables `PRAGMA journal_mode=WAL` on file-backed SQLite databases**
   `P9-T4 | given a temporary file-backed SQLite database ("Data Source=<temp-path>.db") registered via AddInfrastructure | when services.MigrateDatabaseAsync() runs and "PRAGMA journal_mode;" is queried on the connection | then the scalar result is "wal" (case-insensitive), whereas on the shared in-memory test database ("Mode=Memory;Cache=Shared") MigrateDatabaseAsync succeeds without error and journal_mode remains "memory" | why it matters: enables concurrent reads during writes on file-backed SQLite deployments while keeping in-memory test databases working (P9-D2, PRODUCTION-LAYERS.md "Database").`

### Boundaries

5. **`P9-T5` (`must`) — `OTEL_RESOURCE_ATTRIBUTES` exact `service.name` key boundaries**
   `P9-T5 | given OtlpExportTests hosts with OTEL_EXPORTER_OTLP_ENDPOINT set and OTEL_RESOURCE_ATTRIBUTES set to: (a) "deployment.environment=demo, service.name=svc-trimmed" (leading space after comma, exact key match), (b) "custom.service.name=other" (suffix match only, not exact key), and (c) "deployment.environment=demo,service.name=   " (exact key but whitespace-only value) | when a request triggers OTLP export to FakeOtlpCollector | then in (a) exported resource attributes contain "svc-trimmed" and do NOT contain "mortgage-applications"; in (b) and (c) exported resource attributes contain the default service name "mortgage-applications" | why it matters: tests the exact key-boundary parser on comma-separated segments so neither a suffix key like custom.service.name= nor an empty service.name= suppresses the default service name, while whitespace around valid segments is tolerated (PR #9 /code-review 1).`

6. **`P9-T6` (`must`) — Startup sweep retry waits at least the configured delay (`RR5`)**
   `P9-T6 | given a seeded Pending assessment, FailFirstSweep active, and Assessments:RequeueRetryDelaySeconds = 1 (1,000 ms) in AssessmentWorkerTests.Startup_sweep_failure_is_retried_and_completes_pending_assessment | when the host starts, logs EventName == "RequeueFailed" at timestamp t1, retries after the delay, logs EventName == "PendingRequeued" at timestamp t2, and completes the assessment | then (t2 - t1) >= 800 ms (1,000 ms configured delay minus 200 ms timer jitter tolerance: 1,000 - 200 = 800 ms) | why it matters: proves the worker actually awaits the retry delay between a failed startup sweep and the next attempt rather than tight-looping (Phase 6 RR5).`

### Failure / validation & non-completed outcomes

7. **`P9-T7` (`must`) — `AssessmentProcessingResult.RulesVersion` is `null` on `Failed`, `Skipped`, and `NotFound`, and worker falls back to configured `RulesVersion` on `Failed`**
   `P9-T7 | given assessments that finish as Failed (invalid stored TermYears = 50), Skipped (already Completed/Failed), or NotFound (unknown Guid) in MortgageApplicationServiceTests and AssessmentSpanTests | when ProcessAssessmentAsync(assessmentId) runs | then AssessmentProcessingResult.RulesVersion is null for all three non-Completed outcomes, and on Failed the worker tags the assessment.process span and metrics with assessment.rules_version from AffordabilityOptions.RulesVersion ("1.0") | why it matters: failed/skipped/not-found rows have no stored AffordabilityResult, so RulesVersion on the result record must be null while Failed telemetry still reports the active rules version (Q4, PR #9 /code-review 3).`

### Concurrency / idempotency & detached-entity fallback

8. **`P9-T8` (`nice`) — `UpdateAssessmentAsync` still saves a detached `AffordabilityAssessment` instance**
   `P9-T8 | given a Pending assessment loaded in scope 1, detached (or mutated and passed to UpdateAssessmentAsync in a fresh scope 2 where db.Entry(assessment).State == EntityState.Detached) | when UpdateAssessmentAsync(assessment) is called in scope 2 | then EntityState.Detached triggers db.Assessments.Update(assessment), SaveChangesAsync succeeds, and reloading in scope 3 returns the updated Status and Result/AssessedAt | why it matters: preserves the repository contract of UpdateAssessmentAsync when called with an untracked entity while optimizing the tracked path (PR #8 /code-review 3).`

9. **`P9-T9` (`nice`) — `JsonStrictnessTests` shared `Production` host isolation across `[Theory]` rows**
   `P9-T9 | given JsonStrictnessTests sharing a single Production WebApplicationFactory host across all Production [Theory] rows in BadBodies and Environments | when all 12 theory cases and the fact run | then every Production and Development case still returns 400/415 ProblemDetails without echoing sentinel values and saves 0 rows | why it matters: verifies that reusing one Production host per test class fixture avoids per-row host startup overhead without cross-test state leakage (Phase 3 /code-review 7).`
